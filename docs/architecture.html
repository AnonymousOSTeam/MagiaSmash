Under the hood

Architecture

MagiaSmash separates systems written in C++ from content expressed as data. The two meet through the orx engine's config system and a small shared state section.

The split

Three layers

⚙️

C++ game systems

Compiled, performance-sensitive logic that runs every frame.

  • Fighter — the single combat class used by all combatants
  • GameHUD — health bar, wave and message text
  • MagiaSmash.cpp — Scroll framework glue and the main loop
🐍

Python director

Match flow and orchestration, running in the embedded pocketpy runtime.

  • Builds the arena scene and viewport
  • Spawns each wave's enemies
  • Handles wave transitions, victory and restart
📜

INI content

Every tunable number and colour, in one readable file.

  • Fighters and moves (frame data, damage, hitboxes)
  • Waves, effects, arena bounds
  • UI layout, fonts and colours
The bridge

How C++ and Python talk

Rather than a custom binding layer, both sides share a config section called [MatchState]. C++ publishes state; Python polls it each frame and reacts.

; [MatchState] — written by C++, read by the Python director
[MatchState]
PlayerHealth    = 120
PlayerMaxHealth = 120
PlayerPosX      = 0
EnemiesAlive    = 0
Wave            = 0
WaveScale       = 1
GameState       = Playing
Message         = WAVE 1
MessageTimer    = 0

C++ writes

When the player takes damage, an enemy dies, or the wave advances, the Fighter and GameHUD objects update the relevant keys. GameState reflects the match phase: Playing, GameOver, Victory or Restarting.

Python reads

The director's update(dt) checks EnemiesAlive and Wave to decide when to spawn the next wave, declare victory, or wait for a restart input.

Match flow

The director loop

A stripped-down view of MagiaSmash.py, showing how wave transitions are driven purely by combat state.

def update(dt: float):
  state = get_state_string("GameState")

  # Match over: wait for restart
  if (state == "GameOver") or (state == "Victory"):
    if orx.input.has_been_activated("Restart"):
      request_restart()
    return

  # Final wave cleared: victory
  if (g_wave >= MAX_WAVE) and (get_state_int("EnemiesAlive") <= 0):
    set_state_string("GameState", "Victory")
    return

  # All foes down: brief breather, then next wave
  if get_state_int("EnemiesAlive") <= 0:
    if g_timer == 0.0:
      set_state_string("Message", "WAVE CLEAR!")
    g_timer = g_timer + dt
    if g_timer >= CLEAR_DELAY:
      start_wave(g_wave + 1)
Why one Fighter class? Player and enemies share the same physics integrator, hit detection, damage handling and animation timing. The differences — who is driven by input, who by AI, health, speed, size, damage scale — are all just keys in a config section.
Build

Building from source

MagiaSmash is a premake-generated GNU make project that links against a shared orx library.

Requirements

  • A C++11 compiler, plus make
  • The orx engine source, built as liborx.so
  • X11 and OpenGL development headers

Build a release

make -C build/linux/gmake \
  config=release64 \
  ORX=/path/to/orx

The post-build step copies the orx shared libraries into bin/.

Configurations

debug64MagiaSmashd
profile64MagiaSmashp
release64MagiaSmash
bundle64MagiaSmash

Debug logs to console and asserts; profile adds an FPS and profiler overlay; release is the shipping build. 32-bit and web targets are defined but unbuilt.

One gotcha in the embedded runtime: pocketpy does not unwind with blocks on return. Returning from inside a with orx.config.Section(...) leaves the section pushed and eventually overflows the engine's config stack. The director avoids this by assigning inside the block and returning after it — see get_state_int().
